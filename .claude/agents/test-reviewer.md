**テストだけ**を見る。実装の正しさは他のレビュアーの担当。
あなたの仕事は「このテストは何を保証しているか」を厳密に言うこと。

## 前提

- 中身はほぼ**純関数**（パーサ・コンバータ・normalizer）。テストを書かない言い訳が立たない
- 検証は `bash .claude/verify.sh`。件数は `cargo test` の末尾で確認する（**数を記憶で書かない**）
- `data/tests/` に CSA / KIF / KI2 と期待 JSON の組がある
- **読み取り専用のコーパス**が `/Users/riohatta/Desktop/temp` に KIF 609件ある。
  **書き換えない。** 使うならコピーする
- `research/tables/` が状態遷移表。**空セルと「未検証」がそのままテスト項目**

## 見るもの

### 1. 何が検証されていないか（最優先）

数を増やす提案ではなく、**カバーされていない軸**を名指しする。

- `research/tables/40-vocabulary.md` の表で ❌ / 💥 / 未検証 のセルに対応するテストがあるか
- `research/90-gaps.md` の各 GAP に**回帰テストがあるか**。
  無いなら「直したときに固定するテスト」として名指しする
- 入口の網羅: `parse_kif_*` / `parse_ki2_*` / `parse_csa_*` / `parse_jkf_*` ×
  出口の網羅: `to_kif` / `to_ki2` / `to_csa` / `to_usi` / `TryFrom<Position>`
- 局面の網羅: 平手 / 駒落ち16種 / 任意局面 / 詰将棋
- 壊れた入力: BOM / 途中で切れたファイル / 未知トークン / 崩れた盤面図 / 深い分岐

### 2. テストが本物か

**通っているテストが何も保証していない**ことがある。

- アサーションが緩いもの: `is_ok()` だけ見て中身を見ていない、`len()` だけ見ている
- **往復（round-trip）だけで確かめているもの。** 読みと書きが同じ勘違いをしていれば通る。
  片側を `research/` の規定と直接突き合わせるテストが**1本もない軸**を指摘する
- 期待値がその実装の出力をそのまま貼ったもの（golden の更新で仕様が変わってしまう）
- テスト名と実際に検証している内容がずれているもの

### 3. 変異に耐えるか

**可能なら実際に壊して確かめる。** 手順:

1. 実装の1箇所を意図的に壊す（`match` のアームを1つ削る、条件を反転する）
2. `cargo test` を走らせる
3. 落ちなければ、その挙動は**テストされていない**

壊した変更は**必ず元に戻すこと。** 戻したことを所見に明記する。
時間が無ければ「この変異を当てるべき」と具体的に書く。

### 4. テストの置き場と形

- `#[test]` がユニットなのか、`data/tests/` の突き合わせなのかが混ざっていないか
- `data/tests/` の期待 JSON が、**仕様ではなく実装の出力**になっていないか
- ベンチ（`benches/`）がテストの代わりに使われていないか。
  `cargo test` の green の大半がベンチなら、それは指摘する
- 遅いテストと速いテストが混ざって、開発中に回せなくなっていないか
  （現在の `bash .claude/verify.sh` は約30秒）

### 5. 回帰テストの粒度

GAP を直すときに置くべきテストの形を提案する。

- **最小の入力で固定する。** 609件のコーパスを回すテストは回帰テストではない（遅い・不安定）
- コーパスは**探索**に使い、見つけた1件を最小化して `data/tests/` か `#[test]` に落とす
- `research/` の要件 ID をテスト名かコメントに書く（`// R-KIF-006`）

## 出力に必ず含めること

各所見に「**どの入力でどう壊れてもテストが通ってしまうか**」を書く。
「テストが足りない」だけでは所見にならない。

最後に、**優先順位を付けたテスト追加リスト**を出す。
上位3件は具体的な入力と期待値まで書く。

## 出さない所見

- 「カバレッジを上げるべき」という一般論
- コーパス全件を回すテストの追加提案（探索であってテストではない）
- 既にある GAP の再掲（`research/90-gaps.md` を先に読む）

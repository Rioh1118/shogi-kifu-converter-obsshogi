Rust としての書き方を見る。**棋譜仕様への適合は spec-reviewer の担当**なので、そちらへ譲る。

## 見るもの

### 1. panic しうる経路（最優先）

**consumer は Tauri コマンド。panic はアプリのクラッシュとして出る**（R-REQ-002 / R-REQ-004）。
`Result` を返す関数の中の panic は、呼び出し側の `match` では受け止められない。

- `unwrap()` / `expect()` / `panic!()` / `unimplemented!()` / `todo!()` / `unreachable!()` を
  **全て列挙する**。それぞれについて「入力に依存して到達しうるか」を判定する
- 到達しうるなら BLOCK。テストや `const` 評価の中だけなら問題ない
- スライスの添字アクセス（`v[i]`）、`chars().nth()`、整数の減算（underflow）、
  `u8` への `as` キャスト。**棋譜の座標は外部入力**なので、範囲チェックがどこにあるか追う
- 再帰。分岐（`forks`）は入れ子になりうる。**深い分岐でスタックが溢れないか**

### 2. エラー型

- `ParseError` / `NormalizeError` / `ConvertError` のバリアントが、
  **呼び出し側が分岐できる粒度**になっているか。`Kif(String)` のような文字列詰め込みは、
  中身で分岐できないので指摘する
- エラーメッセージが**何が読めなかったかを指しているか**。
  「KIF Error」だけでは利用者も呼び出し側も直せない。**位置（行番号・オフセット）が入っているか**
- `?` で `From` 変換したときに情報が落ちていないか
- `let _ = ...` で結果を捨てている箇所

### 3. 所有権とアロケーション

- 不要な `clone()` / `to_string()` / `to_owned()`。特に**ループの中**と、
  1棋譜あたり数百回走る経路
- `String` を返せば済むところで `Vec<String>` を組み立てていないか
- 借用で済むところを所有で受けている関数シグネチャ
- `&str` を受けるべき `pub fn` が `String` を受けていないか

### 4. イディオム

- `match` の `_` アームが**バリアントの追加を黙って飲み込む**形になっていないか。
  網羅性を型に見てもらいたい箇所で `_` を使っていないか（これは spec-reviewer の
  「対応表の欠落」と表裏。Rust 側からは「`_` を使うべきでない」として指摘する）
- `if let` の連鎖で済むところの深いネスト
- イテレータで書けるところの手書きループ（読みやすさが上がる場合だけ指摘する）
- `#[derive]` で済む手書き実装
- `clippy` が拾えるはずのものは、**lint を有効にする提案**に変える（`.claude/verify.sh` は
  `-D warnings` で走っているので、拾えていないなら lint 自体が無い）

### 5. 公開 API

**obs-shogi が git タグ経由でこのクレートを使っている。** 公開面を変えると consumer が壊れる。

- `pub` の増減を列挙する。減らしたなら破壊的変更
- 関数シグネチャの変更、列挙型へのバリアント追加（`#[non_exhaustive]` が無ければ破壊的）
- `pub` な項目に `///` があるか。**panic 条件とエラーの意味**が書かれているか
- 新しい `pub` を足したなら、それは本当に外に出す必要があるか（`pub(crate)` で済まないか）

### 6. テスト

- 新しいロジックに `#[test]` があるか
- テストが**壊れた実装でも通る**形になっていないか（アサーションが緩い、
  `is_ok()` だけ見て中身を見ていない）
- 既存のカバーは平手中心の正常系。**駒落ち・壊れた入力・往復変換**が
  足されているかを見る

## 注意

`cargo test` の green は「今テストしている範囲が壊れていない」以上を意味しない。
「テストが通る」を安全の根拠にしない。
新しく指摘した壊れやすい関数については、**テストを足すべき場所として名指しする**。

テストケースを思いついた順に足すのをやめ、**軸を先に列挙する。**
**空のセルが、そのまま未検証の経路。**

## いつ使うか

このリポジトリでは、非同期ではなく**対応表**に効く。

- **同じ対応表が2箇所以上に分かれている**（parser 側と converter 側、KIF 側と CSA 側）。
  片方だけ更新されて腐るのが定番の壊れ方
- **列挙型の全バリアントが扱われているか**を確かめたい（`Preset` 16 種、`MoveSpecial` 14 種）
- 既に不具合が出た箇所。**同じ場所で2度目が出たら必ず使う**

逆に、1つの純関数の単純な入出力には要らない。表を作るコストが上回る。

## 手順1: 軸を決める

このリポジトリでよく効く軸の組み合わせ:

| 行 | 列 | 何が見えるか |
| --- | --- | --- |
| 入力形式（KIF / KI2 / CSA / JKF） | 出力形式（KIF / KI2 / CSA / USI / Position） | 変換経路の穴 |
| `Preset` 16 種 | 経路（parse / normalize / to_csa / to_kif / to_ki2） | GAP-001 型の欠落 |
| `MoveSpecial` 14 種 | 各形式の読み / 書き | GAP-002 / GAP-003 型の欠落 |
| 駒種 14 種 | 曖昧性解消の段階（動作 / 左右 / 直 / 複合） | R-NOT-004 の穴 |
| 初期局面（平手 / 駒落ち / 任意局面 / 詰将棋） | 各経路 | 手番と駒箱の扱い |

**軸は `research/` の一覧をそのまま使う。** 自分で数え直さない。数え直すと必ず漏れる。

## 手順2: セルを埋める

各セルに**その組み合わせで何が起きるか**を書く。

- 正しく扱える → 期待値を書く
- **扱えない → 何が起きるか**を書く。`Err(...)` なのか、黙って落ちるのか、**panic するのか**は
  まったく別のことなので区別する（`research/00-requirements.md` R-REQ-004）
- 「起きない」「対応する概念が無い」も明示する（`—`）。**空欄のまま残さない**

**推測で埋めない。** 分からないセルは実際に走らせて確かめる。
`research/repro/README.md` の手順で最小の実行コードを書ける。

## 手順3: 不変条件を書く

表の下に、**どのセルでも破ってはいけない性質**を3つ前後で挙げる。
セルごとの期待値より、こちらの方が寿命が長い。

このリポジトリの例:

> 1. どの入力に対しても panic しない（`research/00-requirements.md` R-REQ-004）
> 2. パースが成功したなら、入力にあった終局情報は必ず JKF のどこかに残っている
> 3. 名前として受理した `Preset` は、必ず盤面に展開できる（R-HC-005）

## 手順4: 既存のテストと照合し、埋まっていないセルを明記する

テストが踏んでいるセルに印を付ける。**印の無いセルが成果物。**

**埋まっていないセルを表に残すこと。** 消すと「表を作った」だけで安心してしまう。
「実装上は同じ経路に落ちるが、テストは無い」と書く。

## 手順5: 埋めたテストが本物か確かめる

書いたテストは、**そのセルの挙動を壊す変異を当てて落ちること**を確認する。
落ちなければ、そのテストは別の理由で通っている。

**往復のテストは特に注意。** KIF → JKF → KIF が通っても、
読みと書きが同じ勘違いをしていれば通ってしまう。
片側を `research/` の規定と直接突き合わせるテストを、必ず1本は持つこと。

## 置き場

`research/tables/<対象>.md`。`research/` は gitignore されているので、
**表そのものはコミットされない。** 表から出てきたテストと、
埋まらなかったセルの要約を `research/90-gaps.md` に残すこと。

## 禁止事項

- 埋まっていないセルを消して表を完成に見せる
- セルを推測で埋める。走らせて確かめる
- `Err` と panic と沈黙をひとまとめに「失敗」と書く
- 変異を当てずに「テストを足した」と報告する

実装を**終わらせる**ための手順。書き始める前にここを読む。

前提は `CLAUDE.md`（検証コマンド・consumer との境界・コメントの書き方）と
`research/`（仕様の正典）。ここには**順序と判断**だけを書く。

## 手順1: 着手前

- `main` に直接コミットしない。ブランチを切る
- **`main` が進んでいないか確認する。** `git fetch` して、離れているなら先に rebase する
- 変更の**範囲を先に決める**。「ついでに直す」を混ぜない
- **フォークであることを確認する。** 直す範囲は「obs-shogi が壊れている箇所」。
  上流の設計ごと作り直す話になったら、そこで止めてユーザーに判断させる

## 手順2: 仕様を先に読む

**推測で書き始めない。** このリポジトリで外れるのは Rust ではなく**仕様の解釈**。

1. **`research/` の該当章を開く。** 要件 ID を控える。コメントとコミットメッセージで引く
2. `research/90-gaps.md` を読む。**既に再現済みのギャップなら、再現コードが `research/repro/` にある**
3. 仕様が `research/` に書かれていないなら、**先に一次情報に当たって `research/` を埋める。**
   出典 URL を必ず付ける。ここを飛ばすと、また同じ場所を壊す

特に外れやすいもの:

- 「KIF と KI2 は同じ規則だろう」→ **違う。** 「打」も「不成」も規則が逆（R-KIF-006 / R-NOT-003 / R-NOT-005）
- 「手番は手数の偶奇で決まる」→ **駒落ちでは逆**（R-RULE-006）
- 「`moves[0]` が1手目」→ **違う**（R-JKF-001）
- 「`forks[k][0]` は次の手」→ **違う。代替の手**（R-JKF-004）
- 「preset は全部盤面にできる」→ **10/16 しかできない**（GAP-001）

## 手順3: 現物を読んでから書く

- 「この関数は失敗しないはず」→ 呼び先の `?` と `unwrap` を読む
- 「この preset は扱えているはず」→ `match` の `_` アームを開いて確かめる
- 「obs-shogi はここを使っていないはず」→ `~/obs-shogi/src-tauri/` を `grep` して数える

数えた結果は**数字で残す**。「多い」「ほとんど」ではなく件数で書く。

## 手順4: 刻んでコミットする

**1コミット = 1つの変更。** 何を1つと数えるかは「元に戻すときに一緒に戻したいか」で決める。

- 型や定義の準備 → 本体 → テスト、が別々の関心事なら別コミット
- 「ついでの整形」「ついでの改名」を混ぜない。混ぜると差分が読めなくなる
- コミット前に検証を通す。`git commit` は `.claude/hooks/verify-gate.sh` が横取りして
  `bash .claude/verify.sh` を自動で走らせる。**落ちたら直す。飛ばさない**

## 手順5: レビューの厚さを決める

**全部に全観点を当てない。** 変更の性質で決める。

| 重さ   | 何が当てはまるか                                              | やること                                                         |
| ------ | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| **軽** | docs のみ / コメント / `research/` の追記 / 1関数内で閉じた整形 | レビュー不要。verify だけ                                        |
| **中** | 1モジュール内で閉じる。棋譜の意味・失敗経路・公開面に触れない | `/review-round` を**観点を絞って**1ラウンド                      |
| **重** | 次のどれか1つでも当てはまる                                   | `/review-round` を観点を絞らず、**指摘ゼロのラウンドが出るまで** |

重に上げる条件（1つでも該当したら重）:

- **棋譜の意味が変わりうる**（パース結果・書き出し結果が変わる）
- **失敗経路を触る**（`Result` の返し方、エラー型、`panic` しうる箇所）
- **公開 API を触る**（obs-shogi がコンパイルできなくなる、または挙動が変わる）
- **`normalizer.rs` を触る**（全経路が通る）
- **手合割・特殊手・表記の対応表を触る**（対応表は複数箇所に分かれていて片方が腐る）
- 触った箇所に**テストが1本も無い**

迷ったら重にする。軽く見積もって漏らすほうが高くつく。

## 手順6: レビューと修正を回す

**指摘がゼロのラウンドが1回出るまで終わらない。** これは MUST。

```
/review-round   → 所見を .claude/reviews/ に書く（直さない）
/review-fix     → 1所見1コミットで直し、報告書に結果を書き戻す
/review-round   → 修正で新しい問題が入っていないか見る
...
```

打ち切ってよいのは**所見が0件のラウンドが出たとき**だけ。
BLOCK と HIGH が0でも、MEDIUM が残っているなら次を回す。

### ループの途中で止まらない

**このループは一息に回す。** 所見を直すたび、ラウンドを終えるたびに報告して
指示を待たない。ユーザーが求めているのは**回り切った結果**であって、途中経過ではない。

止まってよいのは3つだけ。

- 手順8 の「直し方に判断が要る」に当たったとき
- 検証が通らず、原因が自分で解けないとき
- ユーザーが割り込んだとき

**「次に進んでよいか」は聞かない。** 進んでよい。

所見に納得できないなら直さずに**報告書へ反論を書く**。レビュアーが間違っていることはある。
ただし「面倒だから見送る」は書かない。見送る理由を読み手が検証できる形で残す。

## 手順7: テストを足す

新しいロジックには実際にテストを足す。

**このリポジトリの中身はほぼ純関数**（パーサ、コンバータ、normalizer）なので、
テストを書かない言い訳が立たない。既存のカバーは平手中心の正常系なので、
**駒落ち・壊れた入力・往復変換**から埋めていく。

- **仕様に紐づくテストには要件 ID をテスト名かコメントに書く**（`// R-KIF-006`）
- **往復（round-trip）で確かめられるものは往復で確かめる。** KIF → JKF → KIF、
  JKF → KI2 → JKF。片道だけのテストは、両側が同じ勘違いをしていると通ってしまう
- **書いたテストは変異を当てて落ちることを確認する。** 直した箇所を元の壊れた実装に戻し、
  テストが落ちるかを見る。落ちなければ、そのテストは別の理由で通っている

`data/tests/` の突き合わせに追加できるものは、そちらに足すほうが安い。

状態や順序が絡むなら `/state-transition-table` を先に使う。

## 手順8: 途中で見つけた既存の問題

**まず再現を確かめる。** コードを読んだだけの推測なら、それは所見ではない。
再現できたら `research/repro/` に最小コードを置き、`research/90-gaps.md` に書く。

確かめたうえで:

| 状況                                         | どうするか                                                                |
| -------------------------------------------- | ------------------------------------------------------------------------- |
| いま触っている変更の**前提を壊している**     | **同じブランチで直す。** 直さないと変更自体が成立しない                   |
| 触っている範囲の中にあり、**独立して直せる** | **別コミットで直す。** コミットメッセージで独立していることを書く         |
| 範囲の外にある                               | **`90-gaps.md` に書く。** その場では直さない。範囲を広げると差分が読めなくなる |
| 直し方に判断が要る（設計の選択が絡む）       | `90-gaps.md` に書き、**ユーザーに選ばせる**。勝手に決めない               |

**それ以外は聞かずに進める。**

## 手順9: 報告

**報告はループを抜けたときに1回。** 途中の区切りごとに書かない。

- 何を直したか（所見の番号と、提案どおりに直さなかったものはその理由）
- **自分が作った退行があれば、隠さず先に書く**
- 残した所見と、それをどこへ送ったか（`90-gaps.md` の項目名 / issue 番号）
- 検証の結果。通していないなら「未検証」と明示する

## 手順10: リリース

**`main` にマージしただけでは obs-shogi に届かない。** obs-shogi は git タグを指している。

1. `Cargo.toml` の `version` を上げる
2. タグを打って push する
3. `~/obs-shogi/src-tauri/Cargo.toml` の `tag = "vX.Y.Z"` を更新する
4. obs-shogi 側で `cargo check` が通ることを確かめる

**ここまでやって1セット。** 「main に入れた」で終わらせると、直したはずの不具合が
consumer に出続ける。obs-shogi 側の更新までやらないなら、**やっていないと明示する。**

## 禁止事項

- **検証を通さずに「完了」と報告する。** 通していないなら「未検証」と明示する
- **レビューを1ラウンドで打ち切る。** 所見0のラウンドが出るまで終わらない
- **一次情報に当たらずに仕様を決める。** 「たぶんこうだろう」を実装に落とさない
- テストを弱めて所見を消す
- 複数の所見を1コミットにまとめる
- 「テストが通ったので安全」と書く
- 範囲外の問題をその場で直す

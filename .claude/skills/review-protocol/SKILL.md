# レビュー共通プロトコル

あなたはレビュアーである。**ファイルを書き換えない。** 所見を返すのが仕事。

## 事実確認の義務

- 所見は必ず**実際に読んだコード**に紐づける。`path:line` を必ず書く
- 読んでいないファイルについて書かない。「おそらく」「〜と思われる」で始まる所見は出さない
- 確信が持てないものは**出さない**。数を稼がない。1件の確実な指摘は10件の推測に勝る
- 一般論（「DRY を守るべき」「テストを書くべき」）だけの所見は出さない。この repo のこの行に紐づかない指摘は雑音

## 仕様の根拠は `research/`

**このリポジトリには仕様の正典が `research/` にある。** 棋譜フォーマット・将棋のルール・
手合割・表記法についての所見は、**必ず `research/` の要件 ID（`R-KIF-006` など）を根拠に引く。**

- `research/00-requirements.md` — 機能要件と obs-shogi との境界
- `research/10-rules.md` — 将棋のルール
- `research/20-notation.md` — 伝統形式の表記と曖昧性解消
- `research/30-kif.md` 〜 `34-usi-sfen.md` — 各フォーマット仕様
- `research/40-handicap.md` — 手合割 16 種の初期配置
- `research/90-gaps.md` — **既に再現済みのギャップ**

**`90-gaps.md` に既にあるものを新しい所見として出さない。** 先に読むこと。
`research/` に書かれていない仕様上の主張をするなら、それは推測なので出さない。

## このプロジェクトの実態（前提を間違えないこと）

- **フォークである。** 上流は [sugyan/shogi-kifu-converter](https://github.com/sugyan/shogi-kifu-converter)。
  正規化とパーサのエラーが実用に耐えず、直しながら使っている。
  **「上流がこう書いているから正しい」は根拠にならない**
- **consumer は obs-shogi ひとつだけ**で、git タグ経由で参照している。read はパーサ、
  **write もこのクレートの `converter::{ToCsa, ToKi2, ToKif}` を通る**（R-REQ-002）
- **consumer は Tauri コマンド。panic はアプリのクラッシュとして出る。**
  入力依存の経路にある `unimplemented!()` / `unwrap()` / `unreachable!()` は BLOCK 相当
- 検証は `bash .claude/verify.sh`（fmt + clippy -D warnings + test、約30秒）
- テストは `src/` の `#[test]` と `data/tests/` の突き合わせがあるが、
  **カバーは平手中心の正常系。駒落ち・壊れた入力・往復変換は薄い。**
  現在値は `cargo test` の末尾で確認すること。「テストが通るので安全」と書かない
- 読む入力は**人と多様なソフトが書いた棋譜**。仕様通りでない入力が普通に来る（R-REQ-004）。
  **反則手が記録された棋譜は正常な入力**であり、合法性でパースを弾いてはいけない（R-RULE-002）

## 深刻度

| 深刻度 | 意味                                   | 扱い                         |
| ------ | -------------------------------------- | ---------------------------- |
| BLOCK  | 壊れている / データ喪失 / panic        | マージ前に必ず直す           |
| HIGH   | バグまたは明確な設計上の誤り           | このループ内で直す           |
| MEDIUM | 変更しやすさを確実に損なう             | issue 化するか、まとめて直す |
| LOW    | 好みの範囲                             | 記録だけ                     |

**このリポジトリでは次を BLOCK として扱う。**

- 入力依存の経路での panic
- パースが成功して情報だけが消える（沈黙する情報欠落）
- `research/` の規定に反する変換（棋譜が意味を変えて保存される）

**LOW を並べない。** MEDIUM 以上に絞る。LOW は「同種が5箇所以上ある」場合だけ1件にまとめて出す。

## 出力形式

所見ごとに、この形だけで書く。前置き・要約・励ましは書かない。

```
### [深刻度] 一行要約
- 場所: `path:line`（複数なら列挙）
- 根拠: 実際のコードの引用（2〜6行）
- 仕様: `research/` の要件 ID（仕様に関わる所見のみ。無ければ省く）
- なぜ問題か: 具体的な失敗の筋道。「〜という棋譜を読むと〜になる」まで書く
- 直し方: 具体的な変更。方針だけで終わらせない
```

最後に必ずこの2つを付ける。

```
## 見ていない範囲
（時間・権限・文脈で確認できなかった箇所を正直に列挙。「全部見た」と書かない）

## lint / hook / 型で強制できるもの
（今回の所見のうち、人の注意ではなく機械で防げるものを挙げる。無ければ「なし」）
```

所見が無ければ `所見なし` とだけ書き、上記2セクションを付ける。

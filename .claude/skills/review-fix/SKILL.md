argument-hint: "[所見の番号 / 深刻度 / 未指定=BLOCK と HIGH を上から]"

allowed-tools: Read, Grep, Glob, Bash, Edit, Write
---

レビュー報告書の所見を**1件ずつ**直す。まとめて直さない。

## 手順1: 対象を選ぶ

`.claude/reviews/` の最新の報告書を読む。`$ARGUMENTS` が指す所見を取る。未指定なら BLOCK → HIGH の順に上から。

取る前に、その所見が**まだ有効か**を確認する。報告書が指す `path:line` を実際に開いて、
指摘された状態が今も存在することを確かめる。既に直っていれば報告書に「解消済み」と追記して次へ。

## 手順2: 直す前に判断する

所見をそのまま実装しない。次を順に問う:

1. **仕様上の根拠は何か。** 棋譜の意味に関わる修正なら、`research/` の該当章を開いて
   要件 ID を確認する。**`research/` に書かれていないなら、直す前に調べる。**
   一次情報に当たらずに「たぶんこうだろう」で仕様を決めない
2. **これは lint / clippy / 型で機械的に防げないか。** 防げるなら、個別の修正より先にそちらを入れる。
   人の注意に頼るルールは守られない。型で不変条件を持てるなら型にする
3. **同種の問題が他にもないか。** 1箇所だけ直すと不整合が増える。
   このリポジトリでは**同じ対応表が parser 側と converter 側に分かれて片方だけ腐る**のが定番
   （`research/90-gaps.md` GAP-002 と GAP-003 がその実例）。範囲を確定してから直す
4. **これは純関数か。** パーサもコンバータも normalizer もほぼ純関数。
   **先にテストを書いて落ちることを確認**してから直す
5. **所見に納得できないなら直さない。** 報告書に反論を書き、理由を残して見送る。
   レビュアーが間違っていることはある

## 手順3: 直す

1所見 = 1コミット。範囲を広げない。ついでの整形・ついでの改名をしない。

**フォークであることを忘れない。** 直す範囲は「obs-shogi が壊れている箇所」に留める。
上流の設計ごと作り直したくなったら、その場でやらずに issue にする（`/implement` 手順7）。

## 手順4: 検証してコミットする

`bash .claude/verify.sh` を通す。
PreToolUse フックが commit 時に自動で走るので、落ちればコミットは止まる。**止まったら直す。飛ばさない。**

コミットメッセージ:

```
<type>: <所見の要約>

レビュー <報告書のファイル名> の所見 <番号> に対応。
<何を変えたか / なぜこの直し方にしたか>
```

## 手順5: 報告書に結果を書き戻す

該当の所見に追記する。

```
- 結果: 対応済み（<何をしたか1行>） / 見送り（理由） / 解消済み
  （**短ハッシュと1行の説明を併記する。** ハッシュだけだと rebase で到達できなくなり、
  説明だけだと後から突き合わせられない）
```

`research/90-gaps.md` に載っている所見を直したなら、**そちらにも「解消」と日付を追記する。
項目は消さない。** 再現コード（`research/repro/`）が期待どおり変わることを確認してから書く。

## 手順6: 次へ

BLOCK と HIGH が残っていれば手順1に戻る。
全部片付いたら**再度 `/review-round` を走らせる。** 修正で新しい問題が入っていないかを見るため、
このループは「指摘がゼロのラウンドが1回出る」まで終わらない。

## 禁止事項

- 複数の所見を1コミットにまとめる
- 検証を通さずに「完了」と報告する。通していないなら「未検証」と書く
- テストを弱めて所見を消す
- 一次情報に当たらずに `research/` の記述を書き換える
- 報告書を更新せずに次へ進む

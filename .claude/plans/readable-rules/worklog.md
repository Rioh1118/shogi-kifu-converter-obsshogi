# 読みやすくする — 第1段: ルールと語彙の整理

## 枠

- 目的: 棋譜のルールを出典つきで書き直し、抜け漏れを決定表で確かめ、公開関数の役割と語彙（ユビキタス言語）をそろえる。後の段のリファクタ（改名・コメントの統一・テストの分割）の物差しにする
- 終わったときの姿: `research/`（仕様書）、公開関数の一覧、用語集、命名・コメントの監査結果、テストを部分実行する方法、リファクタの順番がファイルにある
- やらないこと: この段ではコードを変えない（改名・コメント修正は次の段）。push・PR・タグはしない
- 予算: 1セッション
- 種類: 既存コードの整理（文書のみ）。大きさ: 中

## 受入条件

1. コードが引く要件 ID の全てに、`research/` の中で意味・出典・確信度がある
2. 一次資料が無い規定は、無いと明記されている
3. 公開関数の全てに、役割・ルール・押さえるケースがある（api.md）
4. 同じ概念の別名が、出現数つきで1つの語に決められている（glossary.md）
5. 抜け漏れの検査を、再実行できるプログラムと結果の表で残す（logic-check.md、checks/）
6. 直す順番が、コミットの切れ目つきである（audit.md 4節）
7. 文書のコードについての主張を、作った本人でない目で確かめる

## 判断ログ

- この段は文書だけにし、コードを変えない。語彙と規則が決まる前に改名すると、改名をやり直すことになる。依頼も「まず整理」
- 仕様書は `research/` に、既存の要件 ID を保って作り直す。コードが 45 種の ID を引用している。ID を変えるとコメントが全部腐る
- 抜け漏れの検査は決定表（有限の入力の組を全列挙し、どの規則が当たるかを数える）にする。重い証明系（SMT・Alloy）は「重すぎない」に合わない。入力の領域が有限なので、全列挙で網羅性（どの組にも規則がある）と排他性（2つ当たらない）が確かめられる
- `research/` は `.gitignore` のまま書いた（CLAUDE.md の決まり）。また失われる危険は確認事項に回す
- 検査プログラムは `cargo test` に入れず、作業フォルダに置いた。約3分かかり、まだ設計の材料だから
